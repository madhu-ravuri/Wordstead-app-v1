# Wordstead Product Specification

## 1. Overview

Wordstead is a local-first writing progress tracker for people working on multiple writing projects. It records a starting word count for each project and individual writing sessions, then presents project totals and daily writing activity in sparklines. The application has no account or server-side data store: project and session data stay in the user's browser unless explicitly exported.

The product is a responsive static web application suitable for free hosting on GitHub Pages. The supplied `mockup.png` is the visual source of truth for the dashboard, and `project page mockup.png` is the visual source of truth for the individual project view. Other screens extend the visual language of these references without changing their core hierarchy.

**Approved layout deviation (Phase 1 review):** The app uses a "postcard" composition: the masthead sits above a single cream paper panel on the coral field, and the overall chart (dashboard) and project sparkline (project detail) sit inside that panel, to the right of the project content on wide layouts, rather than on the coral field outside it as drawn in the mockups. The mockups remain the reference for palette, typography character, pill treatments, chart styling, and information hierarchy.

### Recommended technology

- **Vite, React, and TypeScript:** a small, widely supported front-end toolchain that produces static assets and can be hosted directly from GitHub Pages. Client-side routing, if used, must support GitHub Pages' static-hosting constraints.
- **IndexedDB:** browser-native structured storage suited to projects, sessions, and retained deleted-project records. It avoids a network dependency and generally offers more capacity than `localStorage`.
- **Versioned JSON backup files:** portable, human-readable export/import format for all application data.
- **CSS and lightweight SVG chart rendering:** CSS can implement the responsive scrapbook-inspired layout; simple SVG paths, markers, and star shapes suit the custom sparklines without requiring a hosted chart service.

All core workflows must work offline after the static assets have loaded. The app must not require a backend, paid service, account, or build-time secret.

## 2. Goals and Non-Goals

### Goals

- Track multiple active and completed writing projects.
- Preserve an initial word count separately from words written in the app.
- Record, correct, and remove individual writing sessions, including sessions entered late for a past local date.
- Show accurate project totals and daily writing activity across projects.
- Keep deleted projects' writing activity in overall history.
- Let users back up and restore all stored data.
- Provide a usable, visually consistent experience on phone and desktop.

### Non-goals

- A manuscript editor, document storage, or automatic word counting from notes or manuscript files.
- Goals, target word counts, or projected completion rates in the initial version.
- A browsable archive/history screen for deleted projects in the initial version.
- A running-total chart mode or event-by-event chart tooltips in the initial version.

## 3. User Stories

1. As a writer starting a new story, I want to create a project with a zero starting count so its total grows only from sessions I log.
2. As a writer continuing a story, I want to enter its existing word count so the project total reflects its current manuscript length.
3. As a writer, I want to log multiple sessions for a project on a day and correct or delete any one of them later.
4. As a writer, I want to enter a session for an earlier date when I forgot to log it at the time.
5. As a writer, I want to see each project's total and recent daily writing pattern at a glance.
6. As a writer working on several stories, I want an overall chart that sums daily session words across all projects.
7. As a writer, I want completed projects kept separate from active work while their history remains available in the overall chart.
8. As a writer, I want deleting a project to leave its writing activity in my overall history.
9. As a writer, I want to export and restore all of my data without creating an account.
10. As a writer, I want the dashboard and its key actions to remain practical on a phone.

## 4. Data Model

The storage format must be versioned so future releases can migrate backups and browser data.

### Project

| Field               | Type                        | Rules                                                             |
| ------------------- | --------------------------- | ----------------------------------------------------------------- |
| `id`                | Stable unique identifier    | Generated by the app; preserved by export/import.                 |
| `title`             | String                      | Required after trimming whitespace; duplicate titles are allowed. |
| `startingWordCount` | Integer from 0 to 1,000,000 | Defaults to `0`; included in project total, never in charts.      |
| `deadline`          | Local calendar date or null | Optional.                                                         |
| `synopsis`          | String or null              | Optional plain text.                                              |
| `notes`             | String or null              | Optional plain text; never automatically counted.                 |
| `createdAt`         | Local date/time metadata    | Used to determine project age for chart range.                    |
| `updatedAt`         | Local date/time metadata    | Updated when project fields or status are edited.                 |
| `completedAt`       | Local date/time or null     | Non-null while complete; null while active.                       |
| `deletedAt`         | Local date/time or null     | Non-null after soft deletion; record and sessions are retained.   |

### Writing session

| Field       | Type                        | Rules                                                                       |
| ----------- | --------------------------- | --------------------------------------------------------------------------- |
| `id`        | Stable unique identifier    | Generated by the app; each session remains individually editable/deletable. |
| `projectId` | Project identifier          | References the owning project, including a soft-deleted project.            |
| `date`      | Local calendar date         | The date on which the writing occurred; may be in the past.                 |
| `wordCount` | Integer from 1 to 1,000,000 | Positive whole number for this session.                                     |
| `createdAt` | Local date/time metadata    | Date/time the session was logged; distinct from its activity date.          |
| `updatedAt` | Local date/time metadata    | Updated when the session is corrected.                                      |

### Derived values

- **Project total:** `startingWordCount + sum(wordCount for all sessions belonging to the project)`. Includes sessions for completed projects. A soft-deleted project's data is retained, but the project is not shown in active or completed lists.
- The 1,000,000 limit applies to each starting count and individual session entry; a derived project total may exceed 1,000,000 because it sums entries.
- **Daily project activity:** sum of that project's session word counts for a local calendar date. Does not include starting count.
- **Daily overall activity:** sum of session word counts for that local calendar date across every project record, including soft-deleted projects. Does not include starting counts.
- **Project card date last edited:** the later local calendar date of the project's most recent project-field/status edit and the most recently logged session (`createdAt`). This is the date the session was logged, not its activity date (`date`). Correcting a session does not change its log date; deleting a session removes it from this comparison. Project deletion removes the card rather than changing chart activity.

## 5. Features and Acceptance Criteria

### 5.1 Local data and date handling

**AC 1.** On first use, the app initializes an empty local dataset without requesting account details.

**AC 2.** Projects, sessions, completion state, and soft-deletion state persist across reloads in the same browser profile.

**AC 3.** Calendar dates use the user's local timezone. A writing day starts at local midnight and ends immediately before the next local midnight; daylight-saving transitions must not shift a session into an adjacent calendar date.

**AC 4.** The UI identifies that data belongs to the current browser/device and is not synchronized. It must not transmit project content or session data to a server.

### 5.2 Create and edit projects

**AC 1.** A user can open a new-project form from the dashboard's `+` action.

**AC 2.** The form accepts a required title and optional starting word count, deadline, synopsis, and plain-text notes.

**AC 3.** An omitted starting word count is stored as zero. Entered starting counts must be whole numbers from 0 through 1,000,000 inclusive; invalid input prevents saving and receives an actionable validation message.

**AC 4.** A title containing only whitespace is rejected. The saved title is trimmed. Titles need not be unique.

**AC 5.** Notes are stored and displayed as plain text. The app does not parse notes or synopsis for words and does not count either toward a project total.

**AC 6.** Saving a valid project creates it as active and sets its creation/edit metadata. Its project total initially equals its starting word count.

**AC 7.** A user can edit all project fields. Saving updates project edit metadata; changing the starting count recalculates the displayed total without creating chart activity.

**AC 8.** A project may have a past or future deadline. The deadline is informational in this version and does not alter totals or charts.

### 5.3 Log and correct writing sessions

**AC 1.** A user can open a session form from an active project's detail view and enter a word count and local calendar date.

**AC 2.** The date defaults to the current local date. The user can select a past date, but cannot select or save a date later than the current local date.

**AC 3.** Session word counts must be whole numbers from 1 through 1,000,000 inclusive. Zero, negative, fractional, blank, non-numeric, and greater-than-1,000,000 values are rejected with a validation message.

**AC 4.** Each save creates a distinct session record, even when the same project already has one or more sessions on that date.

**AC 5.** Saving a session increases the project total by its word count and increases that date's project and overall daily activity by the same amount.

**AC 6.** A user can edit or delete an individual session from project detail. Editing its date or count recalculates the owning project's total and the affected project/overall daily activity. Deleting it subtracts its contribution from those values.

**AC 7.** Multiple sessions for one project on the same day appear as separate records in session history and are summed for chart points.

**AC 8.** Editing or deleting a session belonging to a soft-deleted project is not available in the initial UI because that project has no archive view. Its retained records remain present in export data.

### 5.4 Project totals and project sparklines

**AC 1.** Every active and completed project card displays its title, date last edited, current word total, and a project sparkline.

**AC 2.** The project total equals starting count plus all saved session counts, independent of session dates.

**AC 3.** The project sparkline contains one point per local calendar day in its displayed range. Each point is the sum of session words for that day; days without sessions have value zero.

**AC 4.** For a project at least seven calendar days old, the chart displays the current local date and previous six local dates. For a project created less than seven days ago, the first point is the earlier of its creation date and its earliest session date, but never earlier than six days before the current local date; the range continues through the current local date. The project chart therefore never shows more than seven days. Sessions dated before that window still count toward the project total and the overall chart.

**AC 5.** The project sparkline plots daily session counts only. Starting count changes do not add points, affect point heights, or mark a day as activity.

**AC 6.** Each day with at least one session has a star marker, even if there are multiple sessions. Days with no sessions have no star marker.

**AC 7.** The line's vertical position reflects each day's actual count, allowing it to rise, fall, or remain level. Illustrative mockup line shapes must not be used as fixed data.

**AC 8.** The project card and detail view display “Date last edited” as the later local calendar date of the latest project-field/status edit and latest session log (`createdAt`), not the session activity date (`date`). Logging a past-dated session uses the date it was logged; correcting a session does not change its log date, and deleting a session removes it from this comparison.

### 5.5 Overall dashboard sparkline

**AC 1.** The dashboard displays an overall sparkline whose daily value is the total session word count across all projects, including completed and soft-deleted projects.

**AC 2.** For a user with activity at least 30 calendar days old, the chart displays the current local date and previous 29 local dates. If the earliest saved session is more recent, the chart begins on that earliest session date and continues through the current local date.

**AC 3.** Every date in the range has a point. Dates without sessions display zero.

**AC 4.** Starting word counts never affect the overall chart. Creating a project with a nonzero starting count creates no writing activity.

**AC 5.** The chart's line and markers represent daily activity. Decorative bars behind the line are visually subdued, have no data encoding, and must not be mistaken for a second data series.

**AC 6.** Editing or deleting a session updates the corresponding overall daily value. Deleting a project does not change any overall chart value because its sessions are retained and continue to count.

**AC 7.** When there are no sessions, the chart shows a clearly labeled empty state rather than implying that starting counts are activity.

### 5.6 Complete, reopen, and delete projects

**AC 1.** A user can mark an active project complete. It is removed from the active section and appears in the completed section without changing its total or session history.

**AC 2.** A user can reopen a completed project. It returns to the active section, and its totals and chart history remain unchanged.

**AC 3.** Completed projects continue contributing session activity to the overall chart.

**AC 4.** Completing or reopening a project does not create writing-session activity.

**AC 5.** Deleting a project requires an explicit confirmation step that identifies the project and explains that its session history remains in overall totals/backup data.

**AC 6.** Confirming deletion soft-deletes the project: it disappears from active and completed lists, but its project and session records remain stored and its sessions continue contributing to overall chart values.

**AC 7.** Cancelling deletion leaves the project and all of its records unchanged.

### 5.7 Project detail and completed projects

**AC 1.** Selecting a project opens a detail view showing its title, current total, optional deadline, synopsis, notes, and session history.

**AC 2.** Session history shows each session as an individual entry with its activity date and word count, including multiple entries on the same date.

**AC 3.** The detail view provides project edit, log-session, complete/reopen, and delete actions appropriate to the project's state.

**AC 4.** A separate completed-projects section lists completed, non-deleted projects and allows opening and reopening them.

**AC 4a.** The active and completed sections each list projects by date last edited (§4), most recent first.

**AC 5.** Empty active, completed, and session-history states provide a clear next action where applicable.

**AC 6.** On wide desktop layouts, the project detail follows `project page mockup.png`: the Wordstead masthead sits above a large cream paper-like panel on the coral background, with project information in the panel and the project's sparkline alongside it.

**AC 7.** A circular pencil-icon button near the upper-right of the project panel opens project editing. It has an accessible name, visible keyboard focus, and a sufficiently large interactive target.

**AC 8.** The project title appears in a prominent pill-shaped treatment. The synopsis follows beneath it; project metadata is presented in aligned rows for last edited date, word count, deadline, and notes. Empty optional fields may be omitted without leaving misleading placeholder values.

**AC 9.** The detail-view sparkline reflects that project's actual daily session counts and follows the range, zero-day, and activity-marker rules in section 5.4; illustrative mockup geometry is not used as data. Bars behind the line are purely decorative in the initial version and do not encode data; the line and star markers are the only activity data.

**AC 10.** Session history and its log/edit/delete actions remain available in the detail view, below or alongside the summary content as the viewport allows.

### 5.8 Export and import

**AC 1.** A low-prominence menu or footer action exposes export and import without competing with the dashboard's primary project/session actions.

**AC 2.** Export downloads one versioned file containing all projects, sessions, metadata needed to restore them, and soft-deleted records. The export includes no credentials because the app has none.

**AC 3.** Import validates file type, schema version, required fields, identifiers, and value constraints before changing stored data. Project IDs and session IDs must each be unique within the imported file; any duplicate ID within that file makes it invalid, even when the duplicate records are identical. An invalid or unsupported file leaves existing data unchanged and displays an error.

**AC 4.** Importing into a non-empty dataset asks the user whether to replace all data or merge. Importing into an empty dataset may proceed after validation without a replace/merge choice.

**AC 5.** Replace makes the imported dataset the complete local dataset, including its soft-deleted records.

**AC 6.** Merge preserves existing and imported records. Records with distinct identifiers are retained; identical identifiers are deduplicated. If matching identifiers contain different content, the app presents a conflict choice before applying changes, and cancelling leaves the dataset unchanged.

**AC 7.** The import confirmation states whether existing data will be replaced or merged. The app applies a successful import atomically so a failed import cannot leave a partial dataset.

**AC 8.** Exported/imported session dates remain the same local calendar dates; restoring data does not reinterpret them through a UTC date conversion.

### 5.9 Responsive design and visual system

**AC 1.** The dashboard follows the mockup's scrapbook-inspired composition: coral/pink field, cream paper-like dashboard surface, deep burgundy display and interface text, white pill-shaped project rows, contrasting shadow/edge accents, and coral project sparkline lines with star markers.

**AC 2.** The overall chart appears to the right of the project list on wide desktop layouts. Its burgundy line and round markers are prominent; cream bars behind it remain subtle and decorative.

**AC 3.** The `+` control is the primary create-project action. Export/import controls remain secondary and unobtrusive.

**AC 4.** The new-project form, session editor, completed-project section, confirmation dialog, and import/export flows use the dashboard's visual language. The project detail follows `project page mockup.png` for its specific hierarchy and composition while retaining that shared palette, typography character, shadows, and paper-inspired treatment.

**AC 5.** On phone-sized viewports, the dashboard stacks its content into a single-column layout, keeps project actions reachable, and places the overall chart first (so the overall trend is seen first), followed by the dashboard heading and `+` action directly above the project list, without horizontal page scrolling. The project detail stacks its information panel and project sparkline, keeps the edit control reachable, and preserves a readable session history without horizontal page scrolling.

**AC 6.** All primary actions are keyboard operable, visible focus is provided, form controls have programmatic labels, chart meaning is available in accessible text, and color alone is not the only way to communicate state.

**AC 7.** Text and controls do not overlap or become clipped at supported viewport sizes. Charts remain legible without forcing the page wider than the viewport.

## 6. Edge Cases

- A user creates a project with no optional fields: it is active, has a zero total, and has no session activity.
- A project has a nonzero starting count and no sessions: its total is nonzero, while its project and overall charts show no activity for that starting count.
- Several sessions share a project and date: each remains individually editable; the chart shows their sum and one activity marker for the day.
- A user attempts to select or submit a future session date: the date is unavailable or rejected with a validation message; no session is saved.
- The user logs a session dated before the project's creation date: retain the entered date; for a project younger than seven days, the sparkline begins at the earlier of creation and earliest session, capped at the seven-day window.
- An edit moves a session to a date outside the visible chart window: update totals and any affected point in range; dates outside the specified range remain outside the chart.
- Deleting the only session on a day leaves that date as zero if it is in the chart range and removes its activity marker.
- A user completes and later reopens a project: neither transition changes chart data.
- A project is deleted after activity was logged: no project card remains, but overall historical points are unchanged.
- User's local timezone changes: stored date-only session values must not shift to adjacent days.
- Daylight-saving changes produce a 23-hour or 25-hour local day: the app still treats the local calendar date as one chart bucket.
- Browser storage is unavailable or full: show a non-destructive error; do not report an unsaved mutation as successful.
- An import contains invalid counts, malformed dates, duplicate project/session IDs within the file, or an unsupported schema version: reject the file and leave existing data unchanged. ID collisions between a valid imported file and existing data follow the merge rules in §5.8 AC 6.
- A title, synopsis, or notes contain long text or markup-like characters: display safely as text, preserve input, and prevent layout overflow or HTML execution.
- There are no projects, only completed projects, or no sessions: each view has a defined empty state and available navigation remains usable.

## 7. Assumptions

1. Sessions remain separate records even when they share a project and date. Daily charts sum them. This preserves the requested ability to edit/delete an individual session.
2. Session dates are local calendar dates, not timestamps chosen by the user. The session form defaults to today and permits earlier dates; future-dated sessions are not offered in the initial version.
3. Project and session metadata use local device time. “Date last edited” compares the calendar date of the most recent project-field/status edit with the latest session log date (`createdAt`), not the session activity date; correcting a session does not change its log date.
4. Completed projects continue to count in the overall chart. A completed project must be reopened before adding another session.
5. Deleted projects are soft-deleted and retained in storage and backups. A deleted-project archive UI is deferred; retained deleted sessions cannot be corrected through the initial UI.
6. Merge import deduplicates stable identifiers. If the same identifier has differing content, the user chooses which version to keep for that conflict; cancellation makes no changes.
7. The project sparkline's seven-day window includes today and the six preceding local calendar dates. The overall chart's 30-day window includes today and the 29 preceding dates.
8. If a project is younger than seven days, its project chart starts at the earlier of its creation date and earliest session date, but no earlier than six days before today, so it never exceeds seven days. If there is no session, it starts at its creation date.
9. The overall chart's range is based on the earliest retained session date, including sessions belonging to deleted projects. If there are no sessions, the chart presents its empty state.
10. Targets, running-total display mode, chart activity tooltips, and deleted-project history are deferred rather than implied by the initial interface.

## 8. Future Versions

- Add a toggle to the overall chart to switch between daily word counts and running total word count over time.
- In running-total mode, show bars behind the overall daily-count line to represent the running total; retain the daily count line as a paired series with an unambiguous legend.
- Explore encoding real data in the bars behind the project-detail sparkline. If adopted, define the encoded measure and a clear legend without changing the daily activity line's meaning.
- Add hover/focus tooltips on the overall sparkline listing activity behind a change, such as sessions logged, projects added, or projects deleted. A deleted project's retained sessions must not be counted a second time as a new chart event.
- Consider an optional target word count for each project. If a project has both a deadline and a target, show the words per day needed to finish on time. Add this only if users find it valuable.
- Add a deleted-project history/archive view so retained project and session data can be browsed and, if desired, restored.
